## Experiment 1 · Does acceptance survive a re-grade to D?

**Prompted by** the eval's own §6 check ("where the pipeline contradicts the
standard"), unprompted by any entry in `INSPIRATION.md`.

**Observation.** A real clip came back `grade: D, score: 25, annotations: 0,
blocking_failures: [], accepted: true` — accepted while the standard says grade
D is not ingested.

**Diagnosis.** Acceptance was derived in two places and they disagreed:

| location | rule |
|---|---|
| `quality_gates.py:892` (`evaluate_clip`) | no blocking failure **AND** grade != D |
| `curation_agent.py:421` (`_regrade`) | revoked acceptance on a blocking failure only |

`_regrade` re-scores a clip once annotations exist — 45 of the 100 points are
unscored before that — so a clip accepted by the cleaning stage kept its
acceptance after re-grading down to D.

**Change.** `_regrade` now takes the re-graded verdict's own `accepted`,
conjoined with the cleaning stage's so a re-grade can only ever *remove*
acceptance (cleaning knows about viewpoint and hands; the quality report must
not overrule it). Commit `01e9f02`. Two tests, one per direction: the D case,
and a cleaning-rejected clip that must not be resurrected.

**Measured.** Same query, same footage, from the run log:

| | rdt-00003 assemble-cabinet |
|---|---|
| before | `[D] … 1/1 accepted, 0 anchors` |
| after | `[D] 1 found → 1/1 indexed → 0/1 accepted, 0 anchors (310 s)` |

Guards after: 982 tests green, ruff clean.

**Improved.** Acceptance is derived in exactly one place. The first test would
have failed on the old code (it asserts `blocking_failures == []` together with
`accepted is False`), so the regression is covered.

**Did not improve — and got worse on paper.** The measured acceptance rate will
*fall*, possibly to near zero. That is the correct direction: the previous
number counted clips scoring 25 with no annotations. Any comparison across this
commit compares two definitions of "accepted" and must say so.

**Cost.** $1.25 — the in-flight run's first 4 queries, discarded by restarting
so all 200 measure one definition rather than a mixture.

## Experiment 3 · What actually caps the grade? (n=6 of 200)

**Prompted by** the partial scorecard contradicting the baseline's reading. Four
of five graded clips reached `L2`/`L3` with 7–9 annotations — so the baseline's
"annotation depth is near zero" was **generalised from one anomalous clip**
(`rdt-00003`: 0/0 anchors, 0 annotations, score 7). That clip is the outlier, not
the pattern.

**Partial scorecard, 6 of 200 queries.**

| step | count | of the step before |
|---|---|---|
| queries asked | 6 | — |
| found candidates | 5 | 83% |
| videos search found | 120 | — |
| survived the pre-download screen | 8 | **7%** |
| tried to collect | 7 | 88% |
| reached the Datalake | 5 | 71% |
| graded | 5 | 100% |
| **accepted** | **2** | **40%** |
| A or B | 0 | 0% |

30 action anchors, 7.5 per accepted clip, 27.3 per usable hour, 1.10 usable
hours, 100% usable time ratio. §6 contradictions: **none** — the acceptance fix
holds under live conditions.

| clip | grade | score | accepted | level | anchors | annotations |
|---|---|---|---|---|---|---|
| rdt-00003 assemble-cabinet | D | 7 | no | L0 | 0/0 | 0 |
| rdt-00004 assemble-chair | D | 53 | no | L2 | 7/8 | 7 |
| rdt-00005 assemble-desk | C | 63 | yes | L3 | 8/9 | 9 |
| rdt-00006 assemble-drawer | C | 55 | yes | L2 | 7/8 | 7 |
| rdt-00007 assemble-lamp | D | 53 | no | L2 | 8/9 | 9 |

**The measurement.** Scores cluster at 53–63 against a per-clip ceiling of 75,
so the question is what the missing points are. Decomposed offline with
`evaluate_clip` over one fixed L3 tree of 9 annotations, varying only the
licence:

| licence | score | grade |
|---|---|---|
| CC-BY | **75** | **B** |
| YouTube standard | 68 | C |
| none / unknown | 65 | C |

Per-clip weights: annotation depth 30 (L3) + tree structure 15 = 45, media 20,
licensing 10 (7 licence + 3 provenance). Gate 3's diversity 25 is dataset-level
and uncreditable per clip, so **75 is the per-clip ceiling** — which is a B.

**Improved.** Nothing was changed; this is a diagnosis.

**What it overturns.** The licence check is worth exactly 7 points and is
**the C/B boundary**. Annotation is not the binding constraint on grade —
licence is. A non-CC clip is capped at 68 and can never be better than a C
however well it is annotated. Grade A remains unreachable per clip at any
licence.

**Cost.** $0 — the decomposition is offline; the partial scoring is free.

**Also corrected.** Spend is **$0.64/query** ($3.86 over 6), not the ~$0.25 the
5-query sample suggested — projecting ~$128 for 200, not ~$50. And screen
survival is **7%** (8 of 120), harsher than the 22.5% that sample showed.

## Experiment 4 · A partial scorecard from an ordered run is biased (n=21 of 200)

**Prompted by** the find rate appearing to collapse: 6 of 21 queries found
candidates (29%) against the 40-query dry run's 70%. Before believing a
regression that large, check the sample.

**Container restart.** The run died at 21 records when the container restarted;
resumed with `--resume`, which matches on `query_id`, so the 21 were kept and 179
remain. No records were lost or double-counted.

**Partial scorecard, 21 of 200.**

| step | count | of the step before |
|---|---|---|
| queries asked | 21 | — |
| found candidates | 6 | **29%** |
| videos search found | 180 | — |
| survived the pre-download screen | 9 | **5%** |
| tried to collect | 8 | 89% |
| reached the Datalake | 6 | 75% |
| graded | 6 | 100% |
| **accepted** | **2** | **33%** |
| A or B | 0 | 0% |

35 action anchors, 7.5 per accepted clip, 28.8 per usable hour, 1.22 usable
hours. Spend $4.35 over 21 = **$0.21/query**, of which $0.15 stranded. Grades: 2
C, 4 D. §6 contradictions: none. 12 of the 21 queries returned *nothing at all*
from search; 3 more found footage and screened all of it out.

**The measurement.** The frozen set is stored in RDT id order and the run walks
it in that order. RDT id correlates with granularity:

| | Atomic + Primitive Skill | Atomic + Primitive + Benchmark |
|---|---|---|
| first 21 | 13 / 21 = **62%** | 15 / 21 = 71% |
| all 200 | 40 / 200 = **20%** | 93 / 200 = 46% |

Atomic tasks are `adjust bottle`, `beat block hammer`, `click alarmclock`,
`cap container` — single-verb fragments that do not exist as findable web video.
The prefix is three times as dense in them as the set is.

**What it means.** The 29% find rate is **not** a regression against the dry
run's 70%; it is a different sample. Any partial scorecard from this run is
biased pessimistic and gets worse the earlier you read it. The **final**
200-query numbers are unaffected — order does not change which queries run.

**Improved.** Nothing changed; this is a caveat that stops a false alarm.

**Did not improve.** The bias is still there for every partial read between now
and the end of the run. Not fixed by reordering mid-flight: that would mix a
biased prefix with a representative remainder and make partial reads harder to
interpret, not easier.

**Cost.** $0.

## Experiment 5 · Two questions asked and never wired

**Prompted by** Shawn setting the goal: valid clips means hands in frame and no
blur. Checking how each is enforced.

**Measured.**

| criterion | how it was enforced |
|---|---|
| hands in frame | `G1-HAND`, blocking, from caption segments — real |
| not blurry | **nothing** — no blur or legibility check existed anywhere |
| screen recording rejected | `is_screen_capture()` — **zero callers repo-wide** |

`grep -rn "is_screen_capture"` returned the definition and one docstring
reference. No caller, no test. The `world` question has been in the prompt,
answered, and billed on every look since it was added, and its answer discarded.
These docs had blamed the Unity screen recording in the clean collection on the
clip predating the question; it did not.

**Changed.** Wired `is_screen_capture()` into the screen. Added `legibility` as a
fourth question in the same look — no extra call — asking whether you can see
what the hands are doing: legible / illegible / unclear, only "illegible"
rejects. Not a variance-of-Laplacian: that measures texture rather than focus,
and on real footage scored 96 against an end card's 4144, so the numeric proxy
ranks a title card above the footage it precedes. Both reject before download,
the last point before paying to fetch and index.

**Improved.** Two rejection reasons that previously could not fire now can:
"frames show a screen, not the world" and "cannot see what the hands are doing".

**Did not improve.** No measurement of how often either fires — that needs the
run. The legibility question's wording is unvalidated: it may reject shaky
worn-camera footage, which is why "unclear" keeps the candidate and why a
calibration set is still the outstanding measurement.

**Cost.** $0. Three tests, including the asymmetry case (unclear and unanswered
must both keep the candidate).

## Experiment 8 · The loop that could not run, and the loop that could not finish

**Prompted by** two scheduled routines producing nothing across a whole day: the
full eval stalled at 34/200, and the hourly auto-research routine fired 7 times
and pushed 0 commits.

### 8a · A 12-hour job cannot be carried by an hourly poke

**Measured.** The eval's own progress, read three times over the day:

| read | records | note |
|---|---|---|
| first | 21 | container restarted, resumed with `--resume` |
| second | 26 | discarded (predate the validity fields) |
| third | 34 | eval process gone, container reclaimed |

**Diagnosis.** The session container lives only while the session is active and
is reclaimed on idle. A keep-alive routine firing hourly wakes the session for
the length of one turn — minutes — and the job dies again in between. At
~2.9 min/query the remaining 166 queries need ~8 h of *continuous* process life;
hourly pokes buy roughly 1/20 of the wall clock they appear to. The earlier "~11
hours" estimate measured the compute, not the host.

**Changed.** Deleted the keep-alive routine (`trig_017U8…`) rather than renewing
it a fourth time, and moved the eval to GitHub Actions, where a job is allowed
to run to completion: `eval.yml` (4 disjoint chunks of 50, `workflow_dispatch`)
and `eval-chunk.yml` (a 20-query daily slice), `timeout-minutes: 330`,
`concurrency: eval`, `if: always()` on the artifact upload. Commit `4caabd2`.

**Improved.** The chunk ladder is verified disjoint by test
(`tests/test_eval_chunking.py` asserts the YAML's `--limit` ladder equals the
ladder the selection logic was tested against), so four chunks cover 200 queries
exactly once with no overlap and no gap.

**Did not improve.** Nothing has run there yet — the workflow needs 6 repository
secrets that only Shawn can add, and they should be rotated first. Until then
the eval is stopped at 34/200, and 34 is a biased prefix (L10).

**Cost.** $0 to build. The stranded spend is the ~$7 already paid for records
that a keep-alive was never going to extend into a full run.

### 8b · A scheduled agent with no MCP tools cannot take its first step

**Measured.** The hourly auto-research routine: 7 fires, 0 commits, 0 pushes,
no failure reported. Trigger-fired sessions are not listed by `list_sessions`,
so the evidence is circumstantial but consistent:

| evidence | value |
|---|---|
| routine's `allowed_tools` | 19 entries, **no `mcp__*` among them** |
| routine's first instruction | `add_repo` … then `register_repo_root` (both MCP) |
| sibling sessions visibly stuck | 3, all on `"Waiting on permission: mcp__…"` |

Two on `mcp__…__get_session`, one on `mcp__Claude_Code_Remote__send_later`. A
non-interactive session that hits a permission prompt has nobody to approve it,
so it blocks until reclaimed — which looks identical, from outside, to a session
that ran and found nothing to do.

**Changed.** Disabled the routine (`trig_01CCzV…`, `enabled=false`) rather than
leaving it to fire silently. Not deleted: the schedule is worth keeping if the
tool grant can be fixed.

**Improved.** Nothing measurable — this removes a false signal, it does not add
a capability. Seven hours of apparent "auto-research ran and found nothing" were
actually seven hours of a blocked first step.

**Did not improve.** The auto-research loop is now not running at all. Restoring
it needs either MCP tools in the grant or a first step that does not need them
(the repo is already cloned in a session that inherits it, so `add_repo` may be
removable outright). Untested.

**Cost.** $0, and 7 fires' worth of spend already sunk.

## Experiment 9 · One invocation, three hosts

**Prompted by** experiment 8's fix creating a new instance of the oldest bug in
this repo. The measurement invocation — start the server, wait for health,
`--resume`, score — was written out twice in YAML (the slice job and the chunk
job) and was about to be written a third time in a systemd unit for the
always-on VM. L1 says a rule derived in two places eventually disagrees; here
the disagreement bills money, because a caller that drops `--resume` pays again
for finished queries and one that starts the server differently measures
something else.

**Changed.** `eval/run.sh` is now the single definition and all three callers go
through it: `eval.yml`'s slice job, `eval-chunk.yml`'s chunk job, and
`deploy/runner/egoexo-eval.service`. It owns the key check (names only, never
values), the server start, the health wait, the record-count delta, and the
scoring pass. The redundant `--score-only` step at the end of chunk 4 is gone —
run.sh already scored the file it wrote.

Also added, so the VM option is buildable the moment a host is picked:
`deploy/runner/{bootstrap.sh, egoexo-api.service, egoexo-eval.service,
egoexo-eval.timer}`. Deliberately platform-neutral: GCE, EC2, Azure and Hetzner
differ in how you get a shell and what you pay, and in nothing this script
touches, so the provider choice does not fork it. The team already has a GCE
instance (`video-searching-api`, us-central1-a) that `deploy.sh` talks to, which
is the cheapest host to try because it exists.

**Measured.** Smoke-tested end to end in demo mode — real server start, real
health wait, real `run_eval` call, no spend and no keys:

| | |
|---|---|
| server | started on the requested port, healthy |
| eval | 1 query, 1 clip graded, record written |
| scorecard | written beside the records |
| record delta reported | `0 -> 1 (added 1)` |
| missing-key guard | exits 1, names the five keys, **prints no values**, spends nothing |

Both workflow files still parse as YAML. 1023 tests pass (up 3), ruff clean.

**Improved.** Four duplicate derivations collapsed to one. Three new tests pin
the property rather than trusting it: every caller reaches `run_eval.py` only
through `run.sh`, `run.sh` still owns the four things the YAML stopped doing,
and the daily schedule is the same wall-clock hour on both hosts — two hosts on
different schedules would quietly buy the same measurement twice.

**Did not improve.** Nothing has been measured on real footage: this is
plumbing, and the scoreboard is still a 34-query prefix. The VM units are
untested on an actual VM — `bootstrap.sh` is syntax-checked and idempotent by
construction, which is not the same as run. And the daily slice is the head of
the frozen set, so it inherits L10's prefix bias; it is comparable to itself
across days, which is what the promotion rule needs, and not to the full 200.

**Cost.** $0.
