# 2026-08-23

## Experiment 1 · The trees the clean collection never got

**Question.** The clean collection holds cut, accepted footage; the store holds
15 clip rows and 4 segments. Why do 13 of 15 clips have no tree, and what does
it take to give them one?

### What was actually wrong — three things, in order of how much they cost

**1. The store had a reader for trees and no writer.** `segments` has a search,
an object vocabulary, an API route and a Library view. Nothing outside the tests
ever wrote a row. `record_refined` lands a clip row when the clip is cut — on
purpose, "cut but not annotated" is a real state — and the tree was meant to
arrive later on the same `video_id`. Nothing brought it. Same shape as L11: a
consumer with no producer is invisible from the outside, because every read path
works and returns nothing.

**2. The looking gate read the un-built private attribute.**

```python
looking = _looking_enabled() and self._gemini not in (None, False)   # before
looking = _looking_enabled() and self._gemini is not False           # after
```

`None` means "no model was injected" — the lazy `gemini` property builds one on
demand. The HTTP routers inject a client and looked; `CurationAgent`, which
injects none, silently never did, **with `LOOK_AT_FRAMES=1` set**. It then fell
through to the caption-only path, which reads `segment.source_text` — and a
pixel-derived anchor carries none. Zero annotations, zero errors, full cost.

Measured on one real clip (`vid_q6o7…`, 10 s, span 0–6.8 s):

| path | result |
|---|---|
| `AnnotatingAgent.label_span` directly | `disassemble-printed-mold`, usable, hands_visible, left hand named, 2 objects, $0.005 |
| `AnnotationAgent.annotate_video` (same span) | **0 annotations, 0 errors**, L0, re-graded D at 39/100 |

Every existing looking test injects `llm=` *and* `_annotating`, which is exactly
why none of them caught it.

**3. Both drops were silent.** A span that comes back unlabelled returned `None`
with no record, and a run that produced nothing returned an empty tree with no
error. "0 annotations, 0 errors" reads as "the footage had nothing in it".

### What changed

`AnnotationStore.put_tree` (merges onto the existing row — `put` replaces, so
building a `Clip` from an annotation run would blank `source_video_id`, the span
it was cut from and the pixel measurements, which are the only copy of a clip's
provenance and what G0-PROV checks). `pipeline/annotate_clean.py` walks the
collection, reconciles first and **only on a lookup that worked**, and caps what
one pass pays for. The gate fix, `_looker` building through the property, and a
named reason on both drop paths.

### Measured, on the real collection

| | before | after |
|---|---|---|
| clip rows | 15 (3 pointing at deleted videos) | 12 |
| segment rows | 4 | **23** |
| clips carrying a tree | 2 of 12 | **10 of 12** |
| clips whose actions name a hand **and** an object | 0 | **7** |
| annotation level | L1 ×2 | L2 ×8 |

The two clips still without a tree, both explained rather than silent:
`vid_gpl3…` is refused outright by **G1-HAND** — no hands in the footage, which
is the junk in the collection being caught instead of labelled — and `vid_3qee…`
had its only span come back "unreadable reply" twice.

**Did not improve.** Three of ~14 spans hit unreadable replies (~20%), which is
the same rate as the older "one clip in five returns no labels" observation and
is now *visible* rather than fixed. The two pre-existing trees (`vid_6z44…`,
`vid_eknsit…`) are still L1/D with no hand named — `vid_eknsit…` is the Unity
screen recording, and it should probably leave the collection rather than be
re-annotated; that is a deletion and needs Shawn. And `valid` in the scorecard
is still computed from the *source* video's tree, not the delivered clip's, so
§0's 8 valid clips and these 7 are not yet the same measurement.

**Cost.** Not itemised by the runner — a defect worth fixing, since every other
paid path in this repo reports its spend. Order of magnitude from the per-call
prices: ~$0.005 a look, 2–4 looks a clip, 9 clips, plus one cleaning pass each.

**Implies.** Two general things. **A capability that must be switched on has to
be switched on in one place**: this is the third instance of the `self.gemini` /
`self._gemini` family, and the first where the wrong read disabled a whole path
instead of crashing. And **a paid pass must always say what it bought** — the
silent-zero was invisible for as long as it existed precisely because nothing
about it looked like an error.

## Experiment 2 · The runner has a host, and this session could not reach it

**Question.** A VM was provisioned for the always-on runner and an SSH key
handed over. Can a Claude Code session bring it up, and if not, what exactly is
in the way?

**What was run.** Key decoded from the session secret (base64, not PEM as
handed over) to `~/.ssh/egoexo`, chmod 600, validated:
`ssh-keygen -y` yields `ssh-ed25519 … claude-cloud@egoexo-runner`, so the key
is well-formed and matches the runner it was minted for. Then four ways to the
host, all through the session's egress:

| path | result |
|---|---|
| `ssh root@<vm>` direct | connect to port 22 timed out |
| `CONNECT <vm>:22` via the HTTPS proxy | `HTTP/1.1 200 Connection Established`, then **no bytes** for 15 s |
| `ssh -o ProxyCommand='nc -X connect …'` | `Connection closed by UNKNOWN port 65535` |
| **control:** `CONNECT github.com:22` | 200, then no banner either |

**What it means.** The control is the finding. A real sshd sends its version
banner unprompted and immediately; github.com's did not arrive either, so the
silence is not the VM. The proxy answers `CONNECT` for any host:port and then
declines to relay anything that is not HTTPS — which is what
`/root/.ccr/README.md` says it does ("not supported: raw-TCP, non-443 HTTPS
ports"), stated as a limitation and not as a symptom. Ports 80, 443 and 2222 on
the VM were equally silent, so this is the transport, not a firewall rule.

**Not established.** Whether the VM is up, whether sshd is listening, and
whether the key is installed in its `authorized_keys` — no probe from here can
distinguish those from the proxy dropping the connection. The runner's first
bootstrap therefore still needs a session with real network access, or the
provider's console.

**What changed instead.** Two things that were going to bite whoever does run
it. `bootstrap.sh` defaulted `REPO` to the private `video-searching-agent`; the
clone carries no credentials by design, so on a fresh VM it fails at the one
moment there is no checkout to read the comment from — now the public mirror.
And `deploy/runner/remote.sh`, the SSH-side entry point that did not exist:
status, logs, deploy (`bootstrap.sh` again — it is idempotent, so there is no
second code path to drift), and `eval-now`, which starts the systemd unit
rather than the eval, so a hand-run measurement lands in the same dated file
with the same `--resume` and the day stays one comparable datapoint. A test
holds that last property, since `remote.sh` runs from a laptop where nobody
sees the unit's flags. The host is not committed — this repo is public, and
`deploy.sh` already resolves its VM address at call time.
